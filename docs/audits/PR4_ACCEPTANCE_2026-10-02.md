## 修复的问题

### P1：同代陈旧保存覆盖较新进度

原普通保存检查了回收站代际，并持有事务级写入锁，但没有检查另一个实例已在同一代提交的较新 revision。两个 Store 先加载同一档案，第二个实例完成保存后，第一个实例仍可用旧内存提交并覆盖其进度。新增回归在修复前复现了覆盖及候选字节变化。

修复使普通保存也在写入锁内核对最新磁盘候选；发现不同的有效新状态时，返回 `STORAGE_RECYCLE_CHANGED`，提示重新启动，并在写入任何主文件或事务候选前拒绝保存。不得在拒绝后用旧内存重试覆盖较新档案。

为保留原协议的失败重试能力，Store 只允许重试本实例已 flush 且逐字节相同的 `.tmp` 提交意图。改变请求内容会被拒绝并保留所有候选。首次保存也保留原随机 profile_id，避免同一请求在 rename 失败后重试时改变原提交字节。新增回归覆盖同代陈旧写入、不同意图重试拒绝和首次保存原样重试。

### Windows 回收站夹具与崩溃判据

核心夹具原来硬编码 `/tmp`，独立子进程也只接受该前缀，无法通过项目 Windows 入口运行。夹具现使用显式 `--test-profile` 所在的可丢弃目录；子进程验证测试文件名、同目录关系和规范路径后才操作锁。

Windows 的自终止进程可能返回退出码 0。崩溃回归改为核对明确的终止前标记、遗留的写入锁和随后真实的死进程锁回收结果。实际玩家存档未读写。
