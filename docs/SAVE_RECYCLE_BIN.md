# 存档回收站（7天）

## 玩家行为

- 「新建游戏」替换现有档案，或「存档与英雄档案 → 删除当前存档」，都会先把完整原档移入回收站，保留精确的7×24小时
- 「存档与英雄档案 → 存档回收站」显示删除时间、保留截止时间（UTC）、剩余期限及恢复按钮
- 恢复不会覆盖任何当前有效档。请先把当前档移入回收站，再恢复所选旧档；两份档案各自保留，不合并金币、物品或交易收据
- 远征或试玩进行中不能删除/替换/恢复；先正常回到营地
- 保留期满后，在下次正常启动或存档管理修改操作中清理。关闭游戏时没有后台任务，也没有服务器定时保证。只打开回收站是只读操作
- 时钟回退时暂停清理，仍保留恢复能力。空间或权限不足时拒绝删除/替换，原档保持不变。没有提前淘汰或数量上限策略

## 保存协议

首次回收之前仍使用原有 `profile.json` 及原有候选恢复策略。首次回收后使用同目录的 `profile.json.recycle/`：

- `index.json` 是包含校验摘要的索引，记录持久化随机槽位ID、当前存档代际和回收记录。第一次回收先创建指向旧根文件的索引，再写归档和新代文件，因此仅剩.bak/.tmp/.bak.tmp的旧档也能在中断后恢复。一个经过写入、flush、读回验证后的原子rename是切换的提交点；一旦出现代际目录却丢失索引，就拒绝猜测恢复，避免旧档复活
- `slots/<32位随机ID>/profile.json` 是当前代际。正常保存仍使用原来的 `.tmp`、`.bak`、`.bak.tmp` 策略，候选恢复只发生在本代，不能把已删除旧档当成当前档恢复
- `entries/<32位随机ID>.json` 是独立完整归档，包含原逻辑档案ID、删除及到期秒数、完整文档快照以及当时存在的主文件/事务候选/旧版迁移备份的原始字节与SHA-256。玩法和经济数据不拆分、不跨档合并
- 新代文档和完整归档都持久写入并校验成功，才能原子更新索引。任何此前失败都保持旧索引和原文件。提交后只退役已经逐字节核对且在完整归档中的候选文件；不扫描、不删除手工备份、损坏副本或其他不相关文件
- 恢复建立新的活动代际，保留原逻辑档案ID与完整玩法数据，只提高存档revision并一次性标记该回收记录已恢复。当前已有有效档时拒绝恢复。重复恢复不会重复发奖
- 索引/归档损坏、未知字段中的不安全路径、校验不符、碰撞或不确定的中断产物一律保留并拒绝相关操作。归档字段从不作为文件路径使用；只能使用经过严格十六进制校验的ID及代码内固定后缀
- 未提交的孤立文件和无法校验的文件不自动清除，避免以整理空间为由销毁唯一可恢复证据。用户手工备份应复制整个保存目录，不能仅复制旧根路径的profile.json。槽位ID不依赖机器、用户名或绝对路径，完整目录备份可以移到新位置，隔离测试覆盖了重命名路径后的恢复
- 离线软件使用系统时钟；可检测相对已持久记录的时间回退，但无法证明操作系统时钟本身准确。协议依赖同一文件系统支持原子rename及Godot的flush；没有承诺硬件断电下超出平台保证的持久性

## 同时写入与崩溃锁

普通保存、加载/迁移、回收、恢复和到期清理整个事务共用一个本机跨进程写入锁。竞争写入会显示「请关闭其他实例后重试」，不会覆盖活动事务。锁使用原子mkdir和随机token命名的所有者文件，只有确证原进程退出才能回收；回收时原子认领该token的文件，不能错删新所有者。活跃/复用PID、缺失/损坏所有者或不确定的锁均保留并拒绝写入。锁元数据不包含玩家经济数据。

Linux使用procfs判断进程是否仍存在；Windows以系统Get-Process的明确「找不到该PID」结果确认退出，查询失败一律保留。PR #4合并前审查已在Windows / Godot 4.7.2隔离夹具中执行真实独立子进程互斥、自终止遗锁和死进程锁回收。进程在创建锁但尚未写好所有者时崩溃会留下不确定锁并阻止写入，需人工核实后处理，不能为了自动继续而冒险清除。

该锁是事务级互斥。普通保存还会在锁内核对磁盘候选，回收代际改变或同代有效revision被另一实例更新后，旧窗口均拒绝写入并提示重启，不改动最新候选。普通保存只允许原实例逐字节重试自己的已flush `.tmp` 意图；改变请求会被拒绝，首次保存失败重试也保留原随机profile_id。这是防止陈旧覆盖的保护，不宣称通用多窗口游玩支持；请保持一个游戏实例。对应复现、拒绝后字节保留及重试回归见[PR #4审查记录](audits/PR4_ACCEPTANCE_2026-10-02.md)。
